# Architecture and discovery

`core/skills` is canonical for original universal methodology, including opt-in capabilities that are not part of the installer's default selection. `optional/vendored` is canonical for redistributable third-party stack/vendor packages, while `optional/catalog.json` records both vendored and referenced third-party modules. Tool adapters materialize approved selections into a project. Project hooks remain project-owned and are never synchronized back automatically.

```text
Agent Kit canonical source
  -> project .agents/skills -> Codex / Kilo / Copilot
  -> validated project .cline/skills mirror -> Cline
  -> generated, git-ignored project .claude/skills link to .agents/skills -> Claude Code (opt-in)
```

Codex uses root `AGENTS.md` plus `.agents/skills`. Cline uses generated `.cline/skills` mirrors and can share root instructions through a small import file. Core and vendored optional selections follow the same canonical-to-mirror path.

Kilo keeps native permissions and custom-agent frontmatter in `.kilo`, while consuming shared project skills from `.agents/skills` where supported. The kit never creates `.kilo/skills`; that would be an uncontrolled third copy. Genuinely tool-specific agents, permissions, schemas, and configuration remain exceptions under their adapter/native directories.

Copilot uses the root or nearest `AGENTS.md`, a small repository-wide `.github/copilot-instructions.md` bridge, and the same `.agents/skills` materialization as Codex and Kilo. The bridge does not duplicate canonical policy because Copilot gives repository-wide instructions precedence over agent instructions; it points back to `AGENTS.md` and the progressive skill-loading contract without redefining them. The optional `.github/agents/project-auditor.agent.md` profile is installed only on request and never runs automatically. No `.github/skills` or other Copilot skill mirror is created.

Copilot is a first-class supported adapter and execution environment. Its validated/preferred role is currently independent read-only audit and second-opinion review. Coding is not claimed as validated, although the general adapter does not block capabilities provided by Copilot; that routing policy can expand later without changing skill ownership or discovery.

Claude Code is an opt-in adapter that keeps `AGENTS.md` and `.agents/skills` canonical. A one-line `CLAUDE.md` imports `@AGENTS.md`; a tracked `SessionStart` hook in `.claude/settings.json` runs the local `.claude/agent-kit/claude-bootstrap.mjs`, which links `.claude/skills` to `.agents/skills` (junction on Windows, relative symlink elsewhere) before native skill discovery. The link is generated and git-ignored, never a committed symlink or copy, so there is still exactly one skill tree. Existing `CLAUDE.md`, settings, hooks, and links are preserved or refused, never overwritten. The installer, the Claude adapter, and `-UpdatePolicies` never write outside the project through a link: [`scripts/install/project-path.mjs`](../scripts/install/project-path.mjs) checks every path component before the adapter or the policy updater writes, and `install.ps1` refuses any link, junction, or reparse point on a destination path before its first write. Details and the trust model are in `adapters/claude/README.md`.

The kit has no model lock. Agent model choice belongs to environment/project configuration.

## Optional source-only security audit

`optional/vendored/security-audit` is a modified third-party package, pinned and documented in its `UPSTREAM.md`. It uses the existing vendored catalog/installer path and recursive distribution, including references, license, and explicit-only Codex invocation metadata in `agents/openai.yaml`. No installer runtime, adapter, permission, default selection, or new hook is required. Codex/Kilo/Copilot use shared `.agents/skills`; Cline uses the existing mirror; Claude uses its existing opt-in link. Actual discovery on a particular host/version is separate from file-distribution validation.

Only an explicit user request naming `security-audit` activates it. Generic security questions, defects, implementation, and release reviews keep their existing primary workflow. Loading the package is not authorization. Codex hosts supporting `allow_implicit_invocation: false` enforce that invocation policy; other hosts use the textual gate and their own available controls. The package does not change root routing or automatically stack core workflows.

The initial contract is one sequential source-only/offline/read-only pass with no execution, delegation, cloud/database MCP, production requests, or secret-value inspection. `confirmed` means statically proven, with explicit source-only/no-runtime markers; runtime-dependent leads require validation. Reports identify instructional limits separately from verified technical controls. Source inspection cannot guarantee that permitted source contains no embedded secret; incidental values must not be retained or disclosed.

Chat is the default output. External file output needs an explicit user-selected path, verified outside the target after link resolution, and safe non-overwriting creation. When those facilities are unavailable, return chat output. The unchanged Copilot Project Auditor is not the required entry point: it has no file-writing tool and its generic severity wording does not define this module's verdict contract. Use a normal explicitly scoped Copilot task; no auditor profile change is made.

## Skill catalog and update planning

[`scripts/install/skill-catalog.json`](../scripts/install/skill-catalog.json) lists every released content version of each distributed skill (core and vendored optional): per version, the releases that shipped it and a SHA-256 of each file after CRLF -> LF normalization, keyed by relative path. Maintainers regenerate it from release tags with `node scripts/install/skill-catalog.mjs generate` (full history and tags required) and verify it with `check`; `validate-kit.mjs` only reads the committed file and requires it to match the working tree for the current VERSION.

[`scripts/install/skill-update.mjs`](../scripts/install/skill-update.mjs) is a read-only planner (`node scripts/install/skill-update.mjs plan --project <dir> [--skills a,b] [--json]`). It inspects `.agents/skills` and `.cline/skills`, classifies each installed kit skill as current, update (an older released version), or conflict (modified, extra, or missing files, links, or special files), skips third-party skills, and blocks skills roots reached through links or outside the project and a `.claude/skills` that is not the link to `.agents/skills`. It never writes. A hash match proves that installed content is identical to a released version, not that Agent Kit installed it.

[`scripts/install/skill-apply.mjs`](../scripts/install/skill-apply.mjs) applies a plan (`node scripts/install/skill-apply.mjs apply --project <dir> [--skills a,b]`). It rebuilds the plan and refuses one that changed, takes `.agent-kit-update.lock` in the project root (recording the operation and the skills and target hashes it will stage; written completely to a private file and hard-linked into place, so it is never seen empty or partial) so only one update runs per project, and verifies the kit source against the catalog. New copies are staged and hash-checked under `.agents/.agent-kit-update/<operation>/` or `.cline/.agent-kit-update/<operation>/`, outside the skills roots, and a write-once journal records each skill's old and new hashes. Each skill is re-verified, then swapped with two renames (live to staging, staged copy to live); if the second rename fails the first is reversed. EPERM, EBUSY, and EACCES (how Windows reports a briefly held file) are retried a few times with short pauses, only when the failed rename changed nothing and the expected state still holds; a rename that reports an error after taking effect is not retried but left for recovery. Every rename target is re-checked to be a skill directory of the project whose parents are real directories. The two renames are not one atomic step: between them the skill is briefly absent. Old copies are removed only when their files match the journal, and directories only when empty; nothing is removed recursively, and completed skills stay updated if a later one fails.

If an update is interrupted, or a rollback fails, the lock, journal, and staged copies remain, plans are blocked, and recovery (`node scripts/install/skill-apply.mjs recover --project <dir>`) resolves it: ownership requires the lock, the staging directory, and the journal to name the same operation, recovery refuses while that process is still running on the same host, and every skill is classified before anything changes. Journals and lock entries are validated against the catalog (known skill names, the expected location, safe relative paths, SHA-256 digests); target paths are derived from the verified project root, never from those files. Immediately before every rename (source and target), deletion, directory creation, file creation, and read of a staged tree, both apply and recovery re-check that each path component from the project root (`.agents` or `.cline`, `skills`, the staging root, the operation directory, `old`, `new`) is a real directory and not a symbolic link or junction, and refuse otherwise; nothing outside the project is moved, read through, or deleted. Node.js offers no `openat`, `renameat`, or `O_NOFOLLOW` for directories, so a process that actively swaps a component in the instant between a check and the system call is not excluded; such a process already has write access to the project. Content checks, which read whole trees, run before the link checks, so the link checks are the last calls before each rename and the window is as short as Node.js allows. It is narrowed, not closed: in a local stress test a process swapping `.agents/skills` for a link in a tight loop still redirected about 1 in 1,000 restores (against about 1 in 250 with the earlier order); no deletion outside the project was observed. Closing it entirely would need native file APIs, which Agent Kit does not use. A temporary lock file left by a crash at the very start of an update (`.agent-kit-update.lock.<operation>.tmp`) blocks nothing and is not removed automatically; delete it by hand. The lock reader treats a lock that disappears while being read as released, and if the private temporary lock file cannot be removed (for example while antivirus holds it), the update does not start, any lock it created is released, and the leftover file is named. A swap that reached its second rename is completed; otherwise the previous version is restored. Copies whose removal was interrupted are finished when every remaining file belongs to the recorded tree with the recorded content. A stage without a journal was interrupted while staging, before any rename, so installed skills are unchanged; its files are removed only if `staging/old` is empty and every staged file is a skill and path declared in the lock and a byte prefix of the kit source whose hash the lock recorded (a crash can leave a file partly written). A journal cut off by a crash is removable when its text is a prefix of (or starts with) that operation's journal header. Any other state, unknown staging entries, an incomplete or pre-intent lock, a changed kit source, or a journal that is invalid for that operation stops with a diagnostic and changes nothing; a previous copy that may contain edits is named so it can be moved away before recovery is rerun.

`install.ps1` exposes these as standalone operations that only validate arguments and call the Node modules: `-UpdateSkills` (apply), `-UpdateSkills -DryRun` (plan), and `-RecoverSkillUpdate`. Explicit `-Skills`/`-OptionalSkills` names narrow the selection; the default `-Skills` value is ignored. `-Skills` must name core skills and `-OptionalSkills` vendored optional modules, as for installation. They refuse `-Tools`, `-NoSkills`, `-UpdatePolicies`, and `-CopilotAuditor`, `-DryRun` requires `-UpdateSkills`, and a non-zero exit from the module becomes a PowerShell error. An ordinary install refuses to run while a lock or staging leftovers exist, and `validate-install.mjs` fails on them.

## Instruction ownership and loading

Each repository's root instructions own routing, precedence, permissions, context-loading policy, the default user-facing communication language, and other always-on constraints. Agent Kit's root `AGENTS.md` governs development of this repository; `templates/project-rules/AGENTS.md` is the canonical starting point merged or adapted into consumer-project root instructions. Each reusable workflow rule has one canonical skill owner; companion skills point to that owner and add only task-local consequences. This avoids maintaining the same checklist in several skills.

Universal always-on policies are owned by managed blocks (`<!-- agent-kit:<policy>:start/end -->`) in `templates/project-rules/AGENTS.md`; this repository's root `AGENTS.md` carries identical blocks and `validate-kit.mjs` enforces parity. The template's blocks define the managed policy set and its order, so adding a policy needs no installer change. `-UpdatePolicies` replaces stale blocks in place and inserts a missing block next to the nearest present managed block (otherwise at the end of the file); it checks every block first, so any malformed, duplicate, or overlapping block refuses the whole update without writing. Markers of policies absent from the template are ordinary project text. A marker counts only when it is the entire logical line; indented, inline, or suffixed marker text is ordinary text, so documentation shows markers indented or in inline code. An exact unindented marker line inside a fenced code block still counts as a marker. Adapters never copy policy text: Claude imports `AGENTS.md` through `CLAUDE.md`, Copilot's bridge points to it, and Codex, Cline, and Kilo read it natively (per their current documentation; confirm on the target tool version). The installer creates `AGENTS.md` only for projects that lack one; `-UpdatePolicies` is the explicit upgrade path for existing projects (`scripts/install/policy-block.mjs`).

Context loads progressively from root instructions to one primary skill, any justified risk companion, the nearest relevant project/module documentation, and task-required references. Projects may name exceptional authoritative documents, but should not preload a documentation tree or maintain an exhaustive context map.

`handoff` is an opt-in core skill, primary only when the user asks to prepare or resume a handoff of unfinished work. It is plain Markdown with no runtime: Prepare records goal, verified work, Git HEAD/branch/status/diff stat, changed files, check status, blockers, and next actions; Resume re-checks the live Git state, stops on any mismatch, and treats earlier checks as unverified. Output stays in chat unless the user names a new file path.

`data-visualization` is an opt-in core skill and is normally primary when the essential problem is chart choice, analytical encoding, truthful comparison, visualization composition, or chart-specific interaction/responsive behavior. `ui` remains primary when those decisions are settled and the task is chiefly component styling or integration. They are companions only when both boundaries are independently material.
