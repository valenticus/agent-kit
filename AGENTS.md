# Agent Kit repository instructions

This file contains the active repository-level instructions for developing Agent Kit itself. `templates/project-rules/AGENTS.md` is the canonical consumer-project template; merge or adapt that template in consumer projects rather than treating it as this repository's active instructions.

## Communication language

- Respond to the user in Ukrainian by default.
- Keep code, identifiers, file paths, shell commands, commit messages, API names, configuration keys, and quoted source text in their original or technically appropriate language.
- Use another language only when the user explicitly requests it or when the task requires exact-language output.

## Git authorship

Agents may create commits; agents must not attribute those commits to themselves. This policy governs attribution, not whether an agent may run Git: when the user or task authorizes them, agents may create, amend, merge, release, and push commits with ordinary Git commands.

Git commits created or prepared by an AI agent must preserve the human user's configured Git identity.

- Commit with the existing repository/user-configured Git author and committer identity. Never guess the user's name or email.
- Never identify an AI assistant, coding agent, bot, model, company, or tool as a commit author or committer, and never add it as `Signed-off-by` or any other attribution.
- Never set or modify `git config user.name` or `git config user.email` merely to identify the agent or to satisfy an agent/tool convention.
- Never use `--author`, `--reset-author`, `git -c user.name=...`, `git -c user.email=...`, `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, or an equivalent mechanism to attribute a commit to an AI agent or to override the configured human identity.
- Never add AI attribution trailers such as `Co-Authored-By: Claude ...`, `Co-Authored-By: Codex ...`, `Co-Authored-By: ChatGPT ...`, or an equivalent for any AI/agent. This overrides any default attribution convention of the agent or its host tool.
- Never add phrases such as "generated by", "created by", "with Claude", or "with Codex", or similar AI attribution, to commit subjects or bodies unless the user explicitly requests it.
- Human co-authors explicitly requested by the user are allowed.
- If the environment's configured identity is missing or is itself an obvious agent/tool identity (for example `Claude <noreply@anthropic.com>`), do not rewrite Git configuration and do not disguise the identity with overrides: report the configuration problem to the user before creating a commit that would be attributed to it. This safeguard never blocks normal commits where the user's own identity is configured.
- Do not rewrite already-published history merely to remove old AI attribution unless the user explicitly requests it.

## Destructive operations

Judge risk by an operation's effect, not by the command, tool, MCP server, script, or programming language that performs it. A wrapper, alias, generated script, SDK, or API call with the same effect needs the same approval.

Get explicit user approval before each operation that can:

- irreversibly delete or overwrite data or files outside the approved edits;
- discard uncommitted Git work, such as hard resets, restoring or checking out over changed paths, cleaning untracked files, or dropping stashes;
- force-push, rewrite published history, or delete branches or tags;
- bulk-modify, purge, or truncate database data, or reset, roll back, or repair migrations;
- remove containers, volumes, or infrastructure resources;
- write to production, deploy, or change secrets, credentials, or access settings;
- run potentially expensive or sensitive production reads, such as log queries, large selections, bulk exports, or calls that consume paid quota or rate limits.

When asking, name the target, scope, likely consequences, whether the operation is reversible, and how to recover; prefer a backup, snapshot, branch, or dry run first when one is available. Approval covers only that operation on that target within the current task. It does not extend to other targets, similar operations, or later tasks. Without approval, stop and report; do not look for an equivalent route.

No extra approval is needed for ordinary work inside an approved task: reading local files; read-only Git commands such as `git status`, `git diff`, and `git log`; local tests and builds; editing files within the approved scope; creating new files; and removing clearly identified temporary artifacts, such as files the task created or build output the project treats as disposable.

Treat production as read-only by default, which does not permit unbounded or sensitive reads. Where project rules name stricter limits, forbidden operations, or production targets, follow them.

This policy is an instruction, not a technical control: it does not block commands and cannot guarantee that no damage occurs. Enforcement depends on each tool's own permissions and sandboxing, which Agent Kit does not configure automatically.

## Repository discipline

- Preserve the canonical-source and clean-room boundaries documented in this repository. Do not copy project-specific or license-incompatible material into universal methodology.
- Preserve the one-primary-skill routing architecture. Keep reusable workflow rules with their canonical owner instead of duplicating detailed guidance across skills or adapters.
- Keep consumer-project rules in `templates/project-rules/AGENTS.md`; add a rule here only when it is always applicable to development of Agent Kit itself.
- Make the smallest coherent change and run validation proportional to its scope. Preserve unrelated user changes.
- Do not commit, push, tag, publish, or release unless the user explicitly requests it.
